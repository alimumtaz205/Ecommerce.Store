# Deployment

Run the .NET API and Angular Node SSR application behind HTTPS on ONE public website origin. Keep the original Batch Tracker deployment separate. Use a staging database copy first. This package is runnable source, not a claim that a public domain, delivery service or business policies have already been activated.

1. Set frontend `src/environments/environment.ts` AND `.development.ts` `siteUrl` to your canonical public origin for the relevant build; keep browser api `/capi`. Rebuild with npm ci && npm run build. Environment files contain public configuration only.
2. On the SSR host set `PUBLIC_ORIGIN=https://your-real-domain`, `SSR_API_ORIGIN=https://your-private-commerce-api-host`, `PORT=4000`. Angular SSR only allows the PUBLIC_ORIGIN hostname (defaults localhost/127.0.0.1 for development). Set API `Commerce__PublicOrigin` to the same real public origin for sitemap. Do not use wildcard host trust. Configure a fixed trusted API origin with a valid certificate; remote HTTP origins are rejected. Never disable Node TLS validation.
3. Publish API with `dotnet publish backend/Nutragea.Commerce.Api -c Release -o publish/api`. Configure `ASPNETCORE_ENVIRONMENT=Production`, ConnectionStrings__MySql, original Jwt keys/issuer/audience, AllowedHosts, Commerce__DataDirectory (absolute persistent protected directory), DataProtection__CertificatePath and optional DataProtection__CertificatePassword. Production startup refuses an unprotected data-protection keyring. Provision a suitable private certificate through your hosting secret store and protect its private key. Keep Data/media and Data/keys across restarts/deploys; old guest access tokens require the original data-protection keys. Back up them together with MySQL. Do not put them under a public static directory.
4. Configure API HTTPS and forwarded-proxy integration for your actual host topology. Current source does not blindly trust incoming forwarded headers. Either use TLS directly to Kestrel or configure only known proxy addresses for TLS termination before HTTPS redirection. Bind internal services privately and restrict access. Configure upstream request/body/time limits. Keep maximum accepted upload <=6MiB end-to-end.
5. Run Node from frontend using npm ci --omit=dev followed by npm run serve:ssr (build first in a build stage). Keep the complete dist/nutragea browser AND server folders. Rebuild after changing domain metadata. Use a process manager/service with restart and logs.
6. Reverse proxy the public domain to Node SSR. It proxies /capi to its fixed API origin. Disable caching for /capi, private pages and HTML; hashed static assets can be cached. The source uses no-store for dynamic content. Preserve Authorization only to your trusted backend. Public HTML only transfers public GET responses; no checkout/secret/auth payloads are in transfer state.
7. Apply migration101 once using an account with temporary DDL permission, then use least-privilege application DB access. Both operational and commerce writers must use the same mutation_guard implementation. Keep database and data files private. Use encrypted MySQL connections with certificate verification in production and secret management appropriate for your host.
8. Complete README activation steps, test real device navigation/checkout, wrong credentials/session expiry, stock reconciliation, documentary-photo consent and policy publication. No sensitive customer details or access codes should enter analytics, access URLs or logs. Configure retention/backups/restore drills according to your real policy.

Rate limits are per API-visible IP: global240/min, public writes30/min, login10/min. Behind a Node reverse proxy the API sees the proxy IP unless you explicitly configure trusted forwarding. This conservative default can constrain a busy store; configure trusted client-IP forwarding and edge rate limiting for your verified deployment, never trust arbitrary X-Forwarded-For headers. Multi-instance/distributed throttling needs shared infrastructure. Shared MySQL locking protects stock across instances; local data/key storage must become securely shared or consistently mounted across instances.

Security is a deployment property too. No independent penetration test, load test, real carrier delivery, or domain-specific legal/food approval is represented by the supplied automated checks. Do not expose development Swagger publicly. Add online payment only through a real provider with server verification/webhooks and idempotent state transitions, never via a browser success flag.
